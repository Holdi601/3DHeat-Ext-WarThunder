# リプレイの読み取り方 {#how-it-reads-a-replay}

このページは、変換ツールが何を読むか、それがどう確かめられたか、そして各列をどこまで信用してよいかを知りたい人向けです。
変換そのものには必要ありません。

読み取りは、アーケードの空戦、シミュレーターの空戦、海戦のクライアントのリプレイで確かめました。
地上戦のサーバーのリプレイでも、2025 年の形式については、[wt_replay_decoder](https://github.com/llama-for3ver/wt_replay_decoder)
の公開サンプルのリプレイでも確かめました。
どの確認も、ある値を、リプレイが別の独立した方法で示している値と比べたものです。ここでは方法と一致の度合いだけを書いています。

## 何を読み、どう確かめたか {#what-is-read-and-the-check}

| 部分 | 状態と確認 |
|---|---|
| ヘッダー、マップ、ミッション、開始時刻、セッション。結果 | すべてのファイル |
| ミッションの設定（ヘッダーの後の blk） | モード、天候、制限、`stars`（日付、時刻、場所） |
| パケットの流れ（2025 年は zlib、2026 年は zstd） | すべてのパケットを区切って読んだ |
| 飛行機の位置と姿勢（2026 年の形式） | 1 秒に 4 サンプル。読み残しのパケットなし。方位は進行方向と一致 |
| 時間より先に来た飛行パケット | ネットワークの乱れの後、クライアントのリプレイの飛行パケットが、ほかのすべての飛行機を、約 0.75 秒後に来る位置で持っていることがあります。先行の量はパケットごとに測られ、先行している各飛行機には、それが表す時刻が与えられます（`selfCheck.flightPacketsRetimed`） |
| 推測航法の補正による飛びのずれ | 推測航法で動いた区間からの段差は、最後に受信した状態から測られるため、クライアントの補正がトラックを切ることはなくなります（[推測航法](aircraft.md#dead-reckoning-and-the-smoother) を参照） |
| 瞬間移動 | ユニットが進めるはずより遠くへ動いたとき、トラックは切られます。まず種類ごとの限界で（飛行機 750 m/s、地上ユニットと艦船 40 m/s、武器 1800 m/s）、次にそれ自身の速さで。切られた箇所はすべて `trackBreaks` に、考えられる原因（リスポーン、ゲームがプレイヤーを動かした、遠くのユニットの補正）と一緒に載ります。切った後は、トラックの行の間のどのステップも、その種類が許す速さを超えません（`selfCheck.stepSpeed`） |
| 地上と艦船の位置（0xF073 / 0xF074） | 読み残しのパケットなし。16 ビットの姿勢から方位、俯仰、横揺れを読む。方位は進行方向と約 2 度以内（中央値）で一致。俯角は 180/65536 度刻み。横揺れの符号を反転すると、ほぼすべての戦車の射撃で、車体と砲塔から求めた砲の向きが命中したユニットを指す。艦船は水面の高さに置かれる |
| 砲塔 | 戦車の砲塔の旋回角と砲の俯角: [砲塔](ground.md#turrets) を参照 |
| 圧縮された地上の高さ | 64 ビットに詰められた位置は、ほとんどのレベルで −100 m から、一部のレベルでは水面の高さから高さを数えます。そのずれは、両方の形で見えたユニットから、リプレイごとに測られます（`selfCheck.packedGroundHeight`） |
| エンティティのストリーム（作成、破棄） | 作成はすべて読み取り。その形式は Dagor Engine の公開されたソースから。War Thunder 自身のコンポーネントの型は、次のコンポーネントの始まりを見つけることで読み飛ばします。各ユニットの車両とプレイヤースロットは、キルと命中の記録が挙げるものと一致（確認したすべての記録で） |
| どのプレイヤーがどのユニットを操縦したか、AI のユニット、艦船、地上の目標 | エンティティのストリームから。すべてのユニットに車両とチームがあり、プレイヤーのユニットにはそのプレイヤーがいる |
| 結果と比べたキル | プレイヤーごとの死亡数は結果と一致。結果のほうがキル数が多いのは、クライアントがすべてのキルを送られていないためです。戦闘が始まった後に始まったリプレイは、その後のキルしか持ちません |
| キル、致命的な命中、重大なダメージ | すべてのファイル |
| 破壊されたモジュール（0xF118） | ユニットと、部品の番号。部品の名前には車両のダメージモデルが必要ですが、それはリプレイには入っていません |
| 放たれた武器（エンティティのストリーム） | 放った地点は、最も近いユニットから約 10〜20 m（中央値）。それが発射したユニットとみなされます |
| 飛行中の武器（0xF0DB） | ミサイル、ロケット、爆弾。それぞれがそのエンティティに結びついています |
| 飛行記録のない爆弾 | 飛行記録のない爆弾は、投下から着弾までの落下を計算します（重力と抵抗。0.1 秒ごとのサンプル。`extrapolated` は true）。海の上で確認しました。着弾の高さがわかっているので、計算した落下は水面から約 15 m 以内で終わります。マッチドキュメントでは、そのような武器は `ballisticImpact` を持ち、`counts.bombsBallistic` がそれを数えます |
| プレイヤーのスロット、チャット | すべてのファイル |
| 爆発、対空砲の炸裂、表彰、発見、天候、ミッションのオブジェクト | 読み取り済み。位置はビューアで目視確認 |
| 録画しているプレイヤーの計器（0xD04A） | その働きで名前を付けている: [コックピットの計器](aircraft.md#cockpit-instruments)。残りは `notNamed` の下 |
| 飛行エントリのそのほかの欄 | 速度、弾数、操縦、エンジン: [飛行エントリ](aircraft.md#flight-entries) |
| イベントの行の姿勢 | イベントの行には、その瞬間のユニットの方位、俯仰、横揺れ、向きのベクトルがすべて入ります |
| プレイヤーの統計とチームのスコア | 戦闘の終わりには、すべての統計がすべてのプレイヤーについて結果と一致します: [リプレイの内部データ](aircraft.md#reflection-data) |
| 武器と車両の名前 | インストールの英語の翻訳から。いくつかの艦船の既定の装甲帯や飛行場のレーダーには、ゲーム内に名前がありません |
| プレイヤーと AI | 結果にあるプレイヤーの行で AI のものはなく、AI でない行はすべて結果のプレイヤーのもの（`selfCheck.identity`） |
| 残骸 | ユニットの死後のサンプルは届き続けます。地上のユニットや艦船の残骸は、そのエンティティが取り除かれるまで `alive` 0 で、1 本のトラックのままです。飛行機は `alive` 0 が最長 60 秒（`selfCheck.wrecks`） |
| 車両の切り替え | プレイヤーのユニットがまだ生きているときに、同じプレイヤーの次のユニットが現れると、そこで終わらせます（放置された車両）。`selfCheck.vehicleSwitch.twoLiveVehicles` は 0 でなければなりません |
| 戦闘モード | [戦闘モード](ground.md#battle-mode) |
| 2026 年のサーバーのリプレイの飛行機 | 2026 年の形式で読む。方位と横揺れの符号は旋回と一致。仮の機体と偵察ドローンはデータを持たない |
| サーバーのリプレイのプレイヤー | スロットの名前で見つける。統計はすべて結果と一致（`selfCheck.players`） |
| 2025 年のサーバーのリプレイと、バージョン 101286 の飛行機 | 読まない。その飛行パケットは形式が違う |

## ユニットへのメッセージ {#messages-to-units}

すべての種類 4 のパケットは、Dagor Engine の daNet の mpi メッセージです。受け取り手のオブジェクトの ID、
そしてその下位 11 ビットがすべて 1 のとき、オブジェクトの拡張 UID、メッセージ ID、ペイロードが続きます。
ユニットへのメッセージは、拡張 UID としてユニットのエンティティ ID を持ちます: `index << 10 | generation`。
確認済み: そのようなメッセージはすべて、その瞬間に生きているエンティティを指しています。

専門的な人のために、読み取ったメッセージを挙げます:

| メッセージ | 内容と確認 |
|---|---|
| 0xF0E9 UnitHitEffects | 1 つの発射物の命中: 射手の uid と、ユニットの座標系での命中点（x は前、y は上、z は左）。飛行機と艦船ではセンチメートル、地上のユニットでは 1 ステップが 20/32768 m（戦車の砲塔の大きさに合わせたもの）。`hitLocalX/Y/Z` はメートル。[射撃](hits.md#gunfire) の `shot` の行になります。ほぼすべての命中とキルの記録の攻撃者はこの射手の中にいます。命中点は射手に面した側にあります |
| 0xF133 UnitOnExplosion | 同じ射手の uid |
| 0xF04B OnUnitDead | `dead` の行。すべてのキルの記録の被害者には、2 秒以内に 1 つあります |
| 0xD047 FmwRpm | エンジンの回転数（`rpm`）。コックピットの回転計と一致 |
| 0xF0B1、0xF0A0 | `gun_shot` の行: 対空砲と砲兵の 1 発ずつの射撃 |
| 0xF01B、0xF01C | `fire_start`、`fire_stop` の行: 40 mm 対空砲の連射（砲の射撃。車両の火災は `fire_on`。[車両の火災](hits.md#vehicle-fires) を参照） |
| 0xF050、0xF033、0xF054、0xF0BD、0xD046 | `bailout`、`repair`、`rearm`、`bullet_rearm`、`reload` の行 |
| 0xD0FE ProjectileHitReplay | 録画しているプレイヤー自身の命中と被弾。武器と弾薬をインストールから名付けたもの（`projectileHitReplays`） |
| 0xF13E、0xF031 | 命中の視覚効果と、ユニットに付けられた効果。どちらも同じユニットへの命中を伴う |
| 0xD041 | 飛行機の防御用の機銃ごとに 1 つ、1 秒に 2 回。その番号は飛行モデルの機銃の武器と一致 |
| 0xD048、0xF117 | 形式は読んだが、意味は不明 |
| そのほか（0xF09A、0xD020、0xF015、0xF04F、...） | メッセージのサイドカーに、そのユニットと欄つきで入ります |

名前はコミュニティのもの（ShioUmiusi/WTACRP、`tools/wrpl_mpi_names.py`）です。

## そのほかに読むもの {#also-read}

- **エンティティのストリームの複製**（0x22、0x23）: エンティティごとのコンポーネントの値のブロック。艦船の修理タイマー、消耗品の数、所有者とチームの変更、エンジンの過熱。`counts.replicatedComponents` に数えられ、値はメッセージのサイドカーに入ります。
- **ミッションスクリプトの動作**（0xF028）と**ヒント**（0xF0EC）: `triggers`、`hints`。**ミッションの進行**（0xF07A、0xF07C）: `missionProgress`。
- **リプレイのカメラ**（0xD043）: [カメラ](ground.md#the-camera) を参照。

## 読まないもの、その理由 {#not-read-and-why}

- **エンティティのメッセージの名前と中身**（0x20、0x21）: クラス番号は、ゲームに組み込まれたリストの中の位置であり、送られてこず、そのデータにもありません。2 つは読みます（車両の火災と消火器）。残りはエンティティとクラス番号つきで丸ごと残します。
- **そのほかの複製されたオブジェクト**（プレイヤースロットとチーム以外の種類）: 読んで残しますが、名前は付けません。確認に使える結果がありません。
- **ほかの飛行機の操縦、スロットル、弾数**: たまにしか更新されません。飛行サイドカーに残り、テーブルには入りません。
- **飛行機の火災**: どのメッセージにも見つかりません。火災の飛行機には `fire_on` の行がありません。
- **投下された武器の名前**: 爆弾やロケットのエンティティには名前がありません。キルの記録が、キルの武器を挙げます。
- **外れた射撃**: リプレイが持つのは命中だけです。

各マッチドキュメントの `counts.messageIdsNotRead` と `selfCheck` は、新しいリプレイが何を持っていて、どれだけよく読まれたかを示します。
