# 讀取回放的方式 {#how-it-reads-a-replay}

本頁供想知道轉換器讀取了什麼、如何核對，以及因此每個欄位該有多信任的讀者閱讀。轉換回放不需要這一頁。

讀取結果已在客戶端回放上核對過（空戰競技、空戰模擬與海戰），也在地面戰鬥的伺服器回放上核對過；2025 年的格式則在 [wt_replay_decoder](https://github.com/llama-for3ver/wt_replay_decoder) 的公開範例回放上核對。每項檢查都會把一個數值與回放以另一種獨立方式說明的值比對；這裡只列出方法與吻合程度。

## 讀取了什麼，以及如何檢查 {#what-is-read-and-the-check}

| 部分 | 狀態與檢查方式 |
|---|---|
| 標頭、地圖、任務、開始時間、工作階段；結算 | 每個檔案 |
| 任務設定（標頭之後的 blk） | 模式、天氣、限制、`stars`（日期、時間、地點） |
| 封包串流（2025 年為 zlib，2026 年為 zstd） | 每個封包都已切分 |
| 飛機位置與姿態（2026 格式） | 每秒 4 個取樣，沒有任何封包未讀取；航向與飛行方向吻合 |
| 提前到達的飛行封包 | 網路暫時卡頓後，客戶端回放的飛行封包有時會把其他每架飛機放在它們約 0.75 秒後的位置。提前量是逐個封包測量的，且提前的每架飛機都會被賦予它所代表的時間（`selfCheck.flightPacketsRetimed`） |
| 航位推算的跳動 | 航位推算序列中的跳動，會從最後收到的狀態開始測量，因此客戶端的修正不再切斷航跡（[航位推算](aircraft.md#dead-reckoning-and-the-smoother)） |
| 瞬移 | 若單位移動的距離超過它能達到的範圍，航跡就會在該處切斷：先依其種類判斷（飛機 750 m/s，地面與船艦 40 m/s，武器 1800 m/s），再依它自己的速度判斷。每次切斷都會列在 `trackBreaks` 中，並附上可能的原因（重生、遊戲移動玩家、遠處單位的修正）。切斷之後，航跡上相鄰列之間的任何移動速度都不會超過其種類所允許的範圍（`selfCheck.stepSpeed`） |
| 地面與船艦位置（0xF073 / 0xF074） | 沒有任何封包未讀取。航向、俯仰與橫滾取自 16 位元姿態：航向與飛行方向在約 2 度內吻合（中位數）；俯仰每步為 180/65536 度；把橫滾的正負號轉換後，幾乎每一發坦克射擊中，由車體與砲塔得出的砲管方向都指向被擊中的單位。船艦位於水面高度 |
| 砲塔 | 坦克的砲塔偏航與砲管俯仰：見[砲塔](ground.md#turrets) |
| 壓縮的地面高度 | 以 64 位元壓縮的位置，在多數地圖上從 -100 m 起算高度，部分地圖則從水面高度起算；此偏移量是在每個回放中，利用同時以兩種形式出現的單位測量得出（`selfCheck.packedGroundHeight`） |
| 實體串流（建立、銷毀） | 每一次建立都已讀取。格式來自 Dagor Engine 公開的原始碼；War Thunder 自己的元件類型則藉由找出下一個元件的起點而跳過。每個單位的載具與玩家槽位，都與擊殺與命中紀錄中所命名的相同，每一筆被核對的紀錄皆然 |
| 誰駕駛哪個單位、AI 單位、船艦、地面目標 | 來自實體串流：每個單位都有其載具與隊伍，每位玩家的單位都有其玩家 |
| 擊殺與結算的比對 | 每位玩家的死亡數與結算相同；結算中的擊殺數較多，因為客戶端不會收到每一次擊殺。在戰鬥開始後才開始的回放，只包含之後的擊殺 |
| 擊殺、關鍵命中、嚴重傷害 | 每個檔案 |
| 被摧毀的模組（0xF118） | 單位與該部位的編號；部位的名稱需要載具的損傷模型，而回放中沒有這個資料 |
| 已釋放的武器（實體串流） | 釋放點距離最近的單位約 10-20 公尺（中位數），該單位被視為發射器 |
| 飛行中的武器（0xF0DB） | 飛彈、火箭與炸彈，每一個都與其實體相連 |
| 沒有飛行紀錄的炸彈 | 沒有飛行紀錄的炸彈，會從釋放到撞擊之間推算其下墜過程（重力與阻力，每 0.1 秒一個取樣，`extrapolated` 為 true）。已在海面上核對，因為那裡的撞擊高度是已知的：推算出的下墜在水面以上約 15 公尺內結束。在對應文件中，這類武器會有 `ballisticImpact`；`counts.bombsBallistic` 會計算它們的數量 |
| 玩家槽位、聊天 | 每個檔案 |
| 爆炸、防空爆炸、獎勵、偵測、天氣、任務物件 | 已讀取；位置在檢視器中以目視核對 |
| 錄製玩家的儀表（0xD04A） | 依其作用命名：[座艙儀表](aircraft.md#cockpit-instruments)；其餘在 `notNamed` 下 |
| 飛行紀錄項目的其他欄位 | 速度、發數、操縱、引擎：[飛行紀錄項目](aircraft.md#flight-entries) |
| 事件列的姿態 | 每個事件列都帶有其單位在該時刻的航向、俯仰、橫滾與視線向量 |
| 玩家統計與隊伍分數 | 戰鬥結束時，每位玩家的每項統計都與結算相同：[反射資料](aircraft.md#reflection-data) |
| 武器與載具名稱 | 來自你安裝目錄中的英文在地化；有些船艦的預設彈帶與機場雷達在遊戲中沒有名稱 |
| 玩家與 AI | 結算中的玩家沒有任何一列是 AI，每一列非 AI 的都是結算中的玩家（`selfCheck.identity`） |
| 殘骸 | 單位死亡後仍會持續送出取樣；地面單位或船艦的殘骸在其實體移除前 `alive` 為 0，且保持為同一條軌跡；飛機的 `alive` 最多保持 0 達 60 秒（`selfCheck.wrecks`） |
| 載具切換 | 若同一玩家的下一個單位出現時，該玩家的上一個單位仍然存活，則會在該處結束（停留在原地的載具）。`selfCheck.vehicleSwitch.twoLiveVehicles` 必須為 0 |
| 戰鬥模式 | [戰鬥模式](ground.md#battle-mode) |
| 2026 年伺服器回放中的飛機 | 以 2026 格式讀取；航向與橫滾的正負號與轉彎吻合；佔位用的飛機與偵察無人機不含任何資料 |
| 伺服器回放的玩家 | 依槽位中的名稱找到；每項統計都與結算相同（`selfCheck.players`） |
| 2025 年伺服器回放與版本 101286 中的飛機 | 未讀取：它們的飛行封包格式不同 |

## 送往單位的訊息 {#messages-to-units}

每個 type-4 封包都是 Dagor Engine daNet 的 mpi 訊息：先是接收者物件的 id，然後（當其低 11 位元全為 1 時）是物件的擴充 UID、訊息 id 與承載資料。送往單位的訊息，其擴充 UID 就是該單位的實體 id，即 `index << 10 | generation`。已核對：每則此類訊息都指向該時刻仍然存活的實體。

對專業讀者而言，訊息的讀取結果如下：

| 訊息 | 內容，以及檢查方式 |
|---|---|
| 0xF0E9 UnitHitEffects | 一發彈丸的命中：射手的 uid，以及單位座標系中的命中點（x 向前、y 向上、z 向左）：飛機與船艦上以公分計，地面單位每步為 20/32768 公尺（配合坦克砲塔的大小）。`hitLocalX/Y/Z` 以公尺為單位。會成為一個 `shot` 列（[射擊](hits.md#gunfire)）。幾乎每筆命中與擊殺紀錄的攻擊者，都在這些射手之中；命中點位於面向射手的那一側 |
| 0xF133 UnitOnExplosion | 同一個射手 uid |
| 0xF04B OnUnitDead | `dead` 列：每筆擊殺紀錄的受害者，在 2 秒內都有一列 |
| 0xD047 FmwRpm | 引擎的轉速（`rpm`）；與座艙的轉速表吻合 |
| 0xF0B1、0xF0A0 | `gun_shot` 列：重型防空與火砲的單發 |
| 0xF01B、0xF01C | `fire_start`、`fire_stop` 列：40 公厘防空砲的連發（開火中的砲；載具上的火勢為 `fire_on`，見[載具火勢](hits.md#vehicle-fires)） |
| 0xF050、0xF033、0xF054、0xF0BD、0xD046 | `bailout`、`repair`、`rearm`、`bullet_rearm`、`reload` 列 |
| 0xD0FE ProjectileHitReplay | 錄製玩家自己的命中與被命中，附武器與彈藥，名稱取自安裝目錄（`projectileHitReplays`） |
| 0xF13E、0xF031 | 命中的視覺效果，以及在單位上播放的效果；它們伴隨同一單位的命中出現 |
| 0xD041 | 飛機的每一門防禦砲各一則，每秒兩次；其索引與飛行模型的砲手武器相符 |
| 0xD048、0xF117 | 格式已讀取，含義不明 |
| 其餘（0xF09A、0xD020、0xF015、0xF04F 等） | 在訊息附屬檔案中，附其單位與欄位 |

名稱採用社群的命名（ShioUmiusi/WTACRP，`tools/wrpl_mpi_names.py`）。

## 還有讀取的內容 {#also-read}

- **實體串流的複製**（0x22、0x23）：每個實體有一組元件數值的區塊：船艦的修理計時器、消耗品數量、擁有者與隊伍的變動、引擎過熱。計入 `counts.replicatedComponents`；數值則在訊息附屬檔案中。
- **任務腳本動作**（0xF028）與**提示**（0xF0EC）：`triggers`、`hints`。**任務進度**（0xF07A、0xF07C）：`missionProgress`。
- **回放攝影機**（0xD043）：見[攝影機](ground.md#the-camera)。

## 未讀取的內容及原因 {#not-read-and-why}

- **實體訊息的名稱與內容**（0x20、0x21）：類別編號是遊戲內建清單中的位置，並未送出，也不在其資料中。其中兩種已讀取（載具的火勢與其滅火器）；其餘則連同其實體與類別編號完整保留。
- **其他複製的物件**（種類不是玩家槽位與隊伍的）：已讀取並保留，但未命名；結算中沒有可用來核對它們的資料。
- **其他飛機的操縱、油門與發數**：只偶爾更新；保存在飛行附屬檔案中，而非表格中。
- **飛機的火勢**：在任何訊息中都找不到；起火的飛機沒有 `fire_on` 列。
- **已釋放武器的名稱**：炸彈或火箭的實體沒有名稱；擊殺紀錄會命名擊殺所用的武器。
- **未命中的射擊**：回放只包含命中。

每份對應文件中的 `counts.messageIdsNotRead` 與 `selfCheck`，會說明新的回放包含什麼，以及讀取的完善程度。
