# 리플레이를 읽는 법 {#how-it-reads-a-replay}

이 페이지는 변환기가 무엇을 읽는지, 그것이 어떻게 확인되었는지, 그래서 각 열을 얼마나 믿을 수 있는지 알고 싶은 사람을 위한 페이지예요. 리플레이를 변환하는 데 이 페이지는 필요하지 않아요.

읽기는 공중 아케이드, 공중 시뮬레이터, 해상 전투의 클라이언트 리플레이와, 지상 전투의 서버 리플레이로 확인했어요. 2025년 레이아웃은 [wt_replay_decoder](https://github.com/llama-for3ver/wt_replay_decoder)의 공개 샘플 리플레이로도 확인했어요. 각 확인은 값을 리플레이가 두 번째 독립된 방법으로 말하는 것과 비교해요. 여기서는 방법과 일치 정도만 적어요.

## 무엇을 읽고, 어떻게 확인했나 {#what-is-read-and-the-check}

| 부분 | 상태와 확인 |
|---|---|
| 헤더, 맵, 임무, 시작 시각, 세션; 결과 | 모든 파일 |
| 임무 설정(헤더 뒤의 blk) | 모드, 날씨, 제한, `stars`(날짜, 시각, 장소) |
| 패킷 스트림(2025년은 zlib, 2026년은 zstd) | 모든 패킷을 프레임으로 나눔 |
| 항공기 위치와 자세(2026 레이아웃) | 초당 4 샘플, 읽지 않은 패킷 없음; 기수 방위가 이동 방향과 일치 |
| 앞서 도착한 비행 패킷 | 네트워크가 잠시 끊긴 뒤, 클라이언트 리플레이의 비행 패킷에는 나머지 항공기 모두가 약 0.75초 뒤에 있을 위치로 들어 있을 때가 있어요. 앞섬은 패킷마다 측정하고, 앞서 있는 각 항공기에는 그것이 나타내는 시각을 줘요(`selfCheck.flightPacketsRetimed`) |
| 추측 항법의 스냅 | 추측 항법 구간에서 나오는 단계는 마지막으로 받은 상태부터 측정해요. 그래서 클라이언트의 보정이 더 이상 궤적을 끊지 않아요([추측 항법](aircraft.md#dead-reckoning-and-the-smoother)) |
| 순간이동 | 궤적은 유닛이 갈 수 있는 것보다 멀리 움직이는 곳에서 끊어요. 먼저 그 종류 기준으로(항공기 750 m/s, 지상과 함선 40 m/s, 무기 1800 m/s), 그다음 자기 속도 기준으로 봐요. 각 끊김은 가능한 원인과 함께 `trackBreaks`에 나열돼요(리스폰, 게임이 플레이어를 옮김, 멀리 있는 유닛의 보정). 끊은 뒤에는 궤적의 행 사이 단계가 그 종류가 허용하는 것보다 빠른 것이 없어요(`selfCheck.stepSpeed`) |
| 지상과 함선 위치(0xF073 / 0xF074) | 읽지 않은 패킷 없음. 16비트 자세에서 기수, 피치, 롤을 읽어요. 기수 방위는 이동 방향과 (중앙값으로) 약 2도 이내로 일치해요. 피치는 180/65536도 단위예요. 롤의 부호를 뒤집으면, 전차가 쏜 거의 모든 사격에서 차체와 포탑으로 된 포의 방향이 맞은 유닛을 가리켜요. 함선은 수면 높이에 있어요 |
| 포탑 | 전차의 포탑 방위각과 포신 피치: [포탑](ground.md#turrets) 참고 |
| 압축된 지상 높이 | 64비트에 압축된 위치는 대부분의 레벨에서 -100 m부터 높이를 세고, 일부 레벨에서는 수면 높이부터 세요. 오프셋은 두 형태로 모두 보이는 유닛으로 리플레이마다 따로 측정해요(`selfCheck.packedGroundHeight`) |
| 엔티티 스트림(생성, 파괴) | 생성은 모두 읽어요. 레이아웃은 Dagor Engine이 공개한 소스에서 가져와요. 워 썬더 고유의 컴포넌트 타입은 다음 컴포넌트가 어디서 시작하는지 찾아서 건너뛰어요. 확인한 모든 기록에서 처치와 피격 기록이 이름을 대는 것과 같은 차량과 플레이어 슬롯이에요 |
| 누가 어떤 유닛을 운전했는지, AI 유닛, 함선, 지상 목표 | 엔티티 스트림에서 가져와요. 모든 유닛은 차량과 팀을, 모든 플레이어의 유닛은 플레이어를 가져요 |
| 결과와 대조한 처치 | 플레이어별 사망 수는 결과와 같아요. 결과 쪽이 처치를 더 많이 세요. 클라이언트가 모든 처치를 받지는 않기 때문이에요. 전투가 시작된 뒤 시작한 리플레이에는 그 뒤의 처치만 있어요 |
| 처치, 치명타, 중대 피해 | 모든 파일 |
| 파괴된 모듈(0xF118) | 유닛과 부품 번호. 부품의 이름은 차량의 피해 모델이 필요한데, 그것은 리플레이에 없어요 |
| 발사된 무기(엔티티 스트림) | 발사 지점은 가장 가까운 유닛에서 약 10-20 m(중앙값)에 있고, 그것을 발사대로 봐요 |
| 비행 중인 무기(0xF0DB) | 미사일, 로켓, 폭탄. 각각 그 엔티티에 붙어요 |
| 비행 기록이 없는 폭탄 | 비행 기록이 없는 폭탄은 발사부터 충돌까지의 낙하를 계산해요(중력과 항력, 0.1초마다 샘플, `extrapolated`가 true). 충돌 높이를 아는 바다 위에서 확인했어요. 계산한 낙하는 물에서 약 15 m 이내에 끝나요. 매치 문서에서 그런 무기는 `ballisticImpact`를 가지고, `counts.bombsBallistic`이 그 수를 세요 |
| 플레이어 슬롯, 채팅 | 모든 파일 |
| 폭발, 대공 포격 폭발, 보상, 탐지, 날씨, 임무 객체 | 읽어요. 위치는 뷰어에서 눈으로 확인했어요 |
| 녹화한 플레이어의 계기(0xD04A) | 하는 일로 이름을 붙였어요: [조종석 계기](aircraft.md#cockpit-instruments). 나머지는 `notNamed`에 있어요 |
| 비행 항목의 나머지 필드 | 속도, 발사 수, 조종, 엔진: [비행 항목](aircraft.md#flight-entries) |
| 이벤트 행의 자세 | 모든 이벤트 행은 그 순간의 유닛 기수, 피치, 롤, 바라보는 벡터를 가져요 |
| 플레이어 통계와 팀 점수 | 전투가 끝날 때 모든 플레이어의 모든 통계는 결과와 같아요: [리플렉션 데이터](aircraft.md#reflection-data) |
| 무기와 차량 이름 | 설치본의 영어 현지화에서 가져와요. 일부 함선의 기본 탄대와 비행장 레이더에는 게임 안에 이름이 없어요 |
| 플레이어와 AI | 결과에 있는 플레이어의 행 중 AI인 것은 없어요. AI가 아닌 행은 모두 결과에 있는 플레이어의 것이에요(`selfCheck.identity`) |
| 잔해 | 유닛의 죽은 뒤 샘플은 계속 와요. 지상 유닛이나 함선의 잔해는 엔티티가 지워질 때까지 `alive` 0이고, 한 궤적으로 남아요. 항공기는 `alive` 0을 최대 60초 동안 유지해요(`selfCheck.wrecks`) |
| 차량 교체 | 같은 플레이어의 다음 유닛이 나타날 때 아직 살아 있는 그 플레이어의 유닛은 거기서 끝나요(차량이 살아 남은 채 남은 것). `selfCheck.vehicleSwitch.twoLiveVehicles`는 0이어야 해요 |
| 전투 모드 | [전투 모드](ground.md#battle-mode) |
| 2026년 서버 리플레이의 항공기 | 2026 레이아웃으로 읽어요. 기수와 롤의 부호가 선회와 일치해요. 자리표시자 항공기와 정찰 드론은 데이터가 없어요 |
| 서버 리플레이의 플레이어 | 슬롯에서 이름으로 찾아요. 모든 통계는 결과와 같아요(`selfCheck.players`) |
| 2025년 서버 리플레이의 항공기와 101286 버전 | 읽지 않아요. 비행 패킷의 레이아웃이 다르기 때문이에요 |

## 유닛에 보내는 메시지 {#messages-to-units}

모든 타입 4 패킷은 Dagor Engine의 daNet에서 온 mpi 메시지예요. 수신 객체의 id가 오고, 그 id의 하위 11비트가 모두 1이면 객체의 ext UID, 메시지 id, 페이로드가 와요. 유닛에 보내는 메시지는 ext UID로 유닛의 엔티티 id를 가져요. 형식은 `index << 10 | generation`이에요. 확인: 그런 메시지는 모두 그 순간에 살아 있는 엔티티를 가리켜요.

전문가를 위해 메시지들의 뜻을 적어요:

| 메시지 | 내용과 확인 |
|---|---|
| 0xF0E9 UnitHitEffects | 발사체 하나의 명중: 사수의 uid와 유닛 좌표(x 앞, y 위, z 왼쪽)에서의 명중 지점. 항공기와 함선에서는 센티미터, 지상 유닛에서는 한 단계가 20/32768 m(전차 포탑 크기에 맞춤). 리플레이 단위로는 `hitLocalX/Y/Z`(m). [사격](hits.md#gunfire)의 `shot` 행이 돼요. 거의 모든 명중과 처치 기록의 공격자는 이 사수들 중에 있어요. 명중 지점은 사수를 향한 쪽에 있어요 |
| 0xF133 UnitOnExplosion | 같은 사수 uid |
| 0xF04B OnUnitDead | `dead` 행: 모든 처치 기록의 피해자에게는 2초 안에 이것이 있어요 |
| 0xD047 FmwRpm | 엔진의 rpm(`rpm`); 조종석의 rpm 게이지와 일치 |
| 0xF0B1, 0xF0A0 | `gun_shot` 행: 중형 대공포와 포병의 한 발씩 |
| 0xF01B, 0xF01C | `fire_start`, `fire_stop` 행: 40 mm 대공포의 연사(포가 쏘고 있는 것; 차량에 붙은 불은 `fire_on`이에요. [차량 화재](hits.md#vehicle-fires) 참고) |
| 0xF050, 0xF033, 0xF054, 0xF0BD, 0xD046 | `bailout`, `repair`, `rearm`, `bullet_rearm`, `reload` 행 |
| 0xD0FE ProjectileHitReplay | 녹화한 플레이어가 명중시킨 것과 맞은 것, 무기와 탄약 포함, 설치본에서 이름을 가져옴(`projectileHitReplays`) |
| 0xF13E, 0xF031 | 명중의 시각 효과, 그리고 유닛에 재생된 효과. 같은 유닛의 명중과 함께 와요 |
| 0xD041 | 항공기의 방어 기관포마다 하나, 초당 두 번. 인덱스는 비행 모델의 사수 무기와 맞아요 |
| 0xD048, 0xF117 | 레이아웃은 읽었지만 뜻은 알 수 없어요 |
| 나머지(0xF09A, 0xD020, 0xF015, 0xF04F, ...) | 유닛과 필드와 함께 메시지 사이드카에 있어요 |

이름은 커뮤니티(ShioUmiusi/WTACRP, `tools/wrpl_mpi_names.py`)가 붙인 것이에요.

## 함께 읽는 것 {#also-read}

- **엔티티 스트림의 복제**(0x22, 0x23): 엔티티마다 컴포넌트 값 블록이 있어요. 함선의 수리 타이머, 소모품의 개수, 소유자와 팀 변경, 엔진 과열이에요. `counts.replicatedComponents`에 세고, 값은 메시지 사이드카에 있어요.
- **임무 스크립트 동작**(0xF028)과 **힌트**(0xF0EC): `triggers`, `hints`. **임무 진행**(0xF07A, 0xF07C): `missionProgress`.
- **리플레이 카메라**(0xD043): [카메라](ground.md#the-camera) 참고.

## 읽지 않는 것과 그 이유 {#not-read-and-why}

- **엔티티 메시지의 이름과 본문**(0x20, 0x21): 클래스 번호는 게임에 들어 있는 목록의 자리이고, 리플레이에 보내지도 않고 그 데이터에도 없어요. 두 가지는 읽어요(차량의 불과 소화기). 나머지는 엔티티와 클래스 번호와 함께 통째로 보관해요.
- **다른 복제 객체**(플레이어 슬롯과 팀이 아닌 종류): 읽고 보관하지만 이름은 붙이지 않아요. 확인할 결과가 없어요.
- **다른 항공기의 조종, 스로틀, 발사 수**: 가끔만 갱신돼요. 비행 사이드카에 보관하고 테이블에는 넣지 않아요.
- **항공기 화재**: 어떤 메시지에서도 찾지 못했어요. 불이 붙은 항공기에는 `fire_on` 행이 없어요.
- **발사된 무기의 이름**: 폭탄이나 로켓의 엔티티에는 이름이 없어요. 처치 기록이 처치한 무기의 이름을 알려 줘요.
- **빗나간 사격**: 리플레이에는 명중만 있어요.

각 매치 문서의 `counts.messageIdsNotRead`와 `selfCheck`는 새 리플레이에 무엇이 있고 그것이 얼마나 잘 읽혔는지 말해 줘요.
