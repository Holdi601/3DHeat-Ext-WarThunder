# 工具如何读取录像 {#how-it-reads-a-replay}

本页面向想了解转换器读取了什么、如何核对，以及每一列数据可信度如何的读者。转换录像并不需要它。

读取过程已在街机空战、模拟空战和海战的客户端录像上进行核对，在地面战斗的服务器录像上进行核对，并且对于 2025 年的布局，还在 [wt_replay_decoder](https://github.com/llama-for3ver/wt_replay_decoder) 的公开示例录像上进行核对。每项检查都会把某个数值与录像以另一种独立方式给出的结果进行比较；这里只给出方法和一致程度。

## 读取了什么，以及如何核对 {#what-is-read-and-the-check}

| 部分 | 状态及核对方式 |
|---|---|
| 文件头、地图、任务、开始时间、会话；结果 | 每个文件 |
| 任务设置（文件头之后的 blk） | 模式、天气、限制、`stars`（日期、时间、地点） |
| 数据包流（2025 年为 zlib，2026 年为 zstd） | 每个数据包都已分帧 |
| 飞机位置和姿态（2026 年布局） | 每秒 4 个采样，没有任何数据包未被读取；航向与行进方向一致 |
| 早于其时间到达的飞行数据包 | 网络卡顿之后，客户端录像的飞行数据包有时会把其他每架飞机都放在约 0.75 秒之后将到达的位置。这个超前量按数据包逐个测量，超前的每架飞机都会被赋予它所代表的时间（`selfCheck.flightPacketsRetimed`） |
| 航位推算的跳变 | 航位推算序列之外的一次跳跃，以最后一次收到的状态为基准进行测量，因此客户端的修正不再切断轨迹（[航位推算](aircraft.md#dead-reckoning-and-the-smoother)） |
| 瞬移 | 当单位移动的距离超过其能够达到的范围时，轨迹会在该处被切断：先按其类型判断（飞机 750 米/秒，地面单位和舰船 40 米/秒，武器 1800 米/秒），再按其自身的速度判断。每次切断都会在 `trackBreaks` 中列出，并注明其可能的原因（重生、游戏移动了玩家、对远处单位的修正）。切断之后，轨迹各行之间的任何一步都不会快于其类型所允许的速度（`selfCheck.stepSpeed`） |
| 地面和舰船位置（0xF073 / 0xF074） | 没有任何数据包未被读取。航向、俯仰和横滚来自 16 位姿态：航向与行进方向的差距在约 2 度之内（中位数）；俯仰每步为 180/65536 度；在横滚符号校正之后，几乎每一次坦克射击中，车体和炮塔给出的火炮方向都指向被命中的单位。舰船位于水面高度 |
| 炮塔 | 坦克的炮塔偏航和火炮俯仰：见 [炮塔](ground.md#turrets) |
| 打包的地面高度 | 以 64 位打包的位置，在多数关卡中其高度从 -100 米算起，在部分关卡中则从水面高度算起；偏移量是在每场录像中，通过同时以两种形式出现的单位测得的（`selfCheck.packedGroundHeight`） |
| 实体流（创建、销毁） | 所有创建都已读取。布局来自 Dagor Engine 公开的源代码；战争雷霆自身的组件类型通过查找下一个组件的起始位置来跳过。对于所有已核对的记录，每个单位的载具和玩家槽位都与击杀和命中记录中所指的相同 |
| 谁驾驶了哪个单位、AI 单位、舰船、地面目标 | 来自实体流：每个单位都有其载具和队伍，每位玩家的单位都有其玩家 |
| 击杀与结果的对照 | 每位玩家的死亡数与结果中的一致；结果中的击杀数更多，因为客户端并不会收到每一次击杀。在战斗开始后才开始的录像，只包含之后的击杀 |
| 击杀、要害命中、严重损伤 | 每个文件 |
| 被摧毁的模块（0xF118） | 单位及部件编号；部件名称需要载具的损伤模型，而录像中并没有该模型 |
| 发射的武器（实体流） | 发射点与最近的单位之间相距约 10-20 米（中位数），该单位被视为发射器 |
| 飞行中的武器（0xF0DB） | 导弹、火箭弹和炸弹，每一个都与其实体相关联 |
| 没有飞行记录的炸弹 | 没有飞行记录的炸弹，其下落过程根据投放到撞击之间的运动推算（重力和阻力，每 0.1 秒一个采样，`extrapolated` 为 true）。已在海上核对，因为撞击高度是已知的：推算的下落在水面约 15 米之内结束。在对局文档中，这类武器带有 `ballisticImpact`；`counts.bombsBallistic` 统计它们的数量 |
| 玩家槽位、聊天 | 每个文件 |
| 爆炸、高射炮炸点、奖励、侦察、天气、任务对象 | 已读取；位置在查看器中以肉眼核对 |
| 录像播放者的仪表（0xD04A） | 根据其作用命名：[座舱仪表](aircraft.md#cockpit-instruments)；其余的在 `notNamed` 之下 |
| 飞行记录的其他字段 | 速度、弹数、操纵、发动机：[飞行记录](aircraft.md#flight-entries) |
| 事件行的姿态 | 每个事件行都带有其单位在该时刻的航向、俯仰、横滚和视线向量 |
| 玩家统计和队伍得分 | 战斗结束时，每位玩家的每项统计都与结果中的一致：[反射数据](aircraft.md#reflection-data) |
| 武器和载具名称 | 来自你安装中的英文本地化；少数舰船的默认弹带和机场雷达在游戏中没有名称 |
| 玩家与 AI | 结果中的玩家没有任何 AI 行，每一个非 AI 的行都属于结果中的某位玩家（`selfCheck.identity`） |
| 残骸 | 单位死亡之后的采样仍会持续出现；地面单位或舰船的残骸在其实体被移除之前 `alive` 为 0，并保持为同一条轨迹；飞机的 `alive` 最多保持为 0 达 60 秒（`selfCheck.wrecks`） |
| 载具切换 | 同一玩家的下一个单位出现时，该玩家仍然存活的单位在那里结束（即被遗弃而仍停留在原地的载具）。`selfCheck.vehicleSwitch.twoLiveVehicles` 必须为 0 |
| 战斗模式 | [战斗模式](ground.md#battle-mode) |
| 2026 年服务器录像中的飞机 | 按 2026 年的布局读取；航向和横滚符号与转弯一致；占位飞机和侦察无人机不携带任何数据 |
| 服务器录像中的玩家 | 在槽位中按名称找到；每项统计都与结果中的一致（`selfCheck.players`） |
| 2025 年服务器录像和版本 101286 中的飞机 | 未被读取：它们的飞行数据包布局不同 |

## 发给单位的消息 {#messages-to-units}

每个类型为 4 的数据包都是 Dagor Engine 的 daNet 的 mpi 消息：先是接收方对象的 ID，然后（当其低 11 位全部为 1 时）是对象的扩展 UID、消息 ID 和负载。发给单位的消息，其扩展 UID 为该单位的实体 ID，即 `index << 10 | generation`。已核对：每条这样的消息都指向当时仍存活的实体。

供专业人士参考，各消息的含义如下：

| 消息 | 内容，以及核对方式 |
|---|---|
| 0xF0E9 UnitHitEffects | 一枚弹丸的命中：射手的 uid，以及单位坐标系中的命中点（x 为前方，y 为上方，z 为左侧）：飞机和舰船上以厘米计，地面单位上每步 20/32768 米（按坦克炮塔的大小拟合）。`hitLocalX/Y/Z` 以米为单位。它会成为一条 `shot` 行（[射击](hits.md#gunfire)）。几乎每条命中和击杀记录的攻击者都在这些射手之中；命中点位于面向射手的一侧 |
| 0xF133 UnitOnExplosion | 同样的射手 uid |
| 0xF04B OnUnitDead | `dead` 行：每条击杀记录的受害者，在 2 秒之内都有一行 |
| 0xD047 FmwRpm | 发动机的转速（`rpm`）；与座舱的转速表一致 |
| 0xF0B1、0xF0A0 | `gun_shot` 行：重型高射炮和火炮的单发射击 |
| 0xF01B、0xF01C | `fire_start`、`fire_stop` 行：40 毫米高射炮的连发（火炮射击；载具上的火源为 `fire_on`，见 [载具火灾](hits.md#vehicle-fires)） |
| 0xF050、0xF033、0xF054、0xF0BD、0xD046 | `bailout`、`repair`、`rearm`、`bullet_rearm`、`reload` 行 |
| 0xD0FE ProjectileHitReplay | 录像播放者自己的命中以及被命中的情况，包括武器和弹药，名称取自安装（`projectileHitReplays`） |
| 0xF13E、0xF031 | 命中的视觉效果，以及在单位上播放的效果；它们伴随同一单位上的命中出现 |
| 0xD041 | 飞机的每门防御火炮各一条，每秒两次；其索引与飞行模型中的炮手武器相对应 |
| 0xD048、0xF117 | 布局已读取，含义未知 |
| 其余（0xF09A、0xD020、0xF015、0xF04F 等） | 连同其单位和字段一起保存在消息附属文件中 |

消息名称来自社区（ShioUmiusi/WTACRP，`tools/wrpl_mpi_names.py`）。

## 另外读取的内容 {#also-read}

- **实体流复制**（0x22、0x23）：每个实体一组组件值：舰船的修理计时器、消耗品数量、所有者和队伍的变化、发动机过热。计入 `counts.replicatedComponents`；其数值保存在消息附属文件中。
- **任务脚本动作**（0xF028）和**提示**（0xF0EC）：`triggers`、`hints`。**任务进度**（0xF07A、0xF07C）：`missionProgress`。
- **录像相机**（0xD043）：见 [相机](ground.md#the-camera)。

## 未读取的内容，以及原因 {#not-read-and-why}

- **实体消息的名称和内容**（0x20、0x21）：类别编号是游戏内置列表中的一个位置，既不会被发送，也不在其数据中。其中两类被读取（载具的火源及其灭火器）；其余的连同其实体和类别编号完整保存。
- **其他复制对象**（玩家槽位和队伍以外的种类）：已读取并保存，但未命名；结果中没有可用来核对它们的内容。
- **其他飞机的操纵、油门和弹数**：只是偶尔刷新；保存在飞行附属文件中，而不在表格中。
- **飞机火灾**：在任何消息中都没有找到；着火的飞机没有 `fire_on` 行。
- **发射出去的武器名称**：炸弹或火箭弹的实体中没有名称；击杀记录会给出造成击杀的武器名称。
- **未命中的射击**：录像只包含命中。

每份对局文档中的 `counts.messageIdsNotRead` 和 `selfCheck` 说明了一份新录像包含哪些内容，以及读取的效果如何。
